# MVP Scoper

Turn a blueprint into three things the user can act on this week: **what to
build first**, **what it will look like**, and **how to explain it to someone
else**. Every run produces exactly three files in `project-blueprint/`:

| File | What it is |
|---|---|
| `mvp-plan.md` | The smallest real slice that proves the idea works, as a Week 1 checklist |
| `mockup.html` | A self-contained, visually designed static mockup of the main screen |
| `one-pager.pdf` | A real single-page marketing PDF — what it does, who needs it, why it matters |

All three are required. Producing two of three is an incomplete run.

## Input

- `project-blueprint/architecture.md` — the components and data flows. The MVP
  plan must build a real path through *these* components.
- `project-blueprint/tech-stack.md` — the chosen technologies. Every build step
  names the actual technology from this file, never a generic placeholder.

Read both fully before writing anything.

If `architecture.md` does not exist, say so and offer to run `/system-architect`
first, then stop. If `tech-stack.md` does not exist, offer to run
`/tech-stack-recommender` first, then stop. Do not invent an architecture or a
stack to plan against — a plan built on guessed components sends the user down
the wrong week.

## Hard rules

- **The MVP is one real end-to-end slice, not a layer.** "Build the database
  schema" is a layer; nobody can use it and it proves nothing. "A user pastes a
  job link and sees a match score" is a slice — thin, ugly, but real from the
  first click to the visible result.
- **Week 1 means one person, one week.** If the checklist could not be finished
  by one person in five working days, it is not an MVP — cut until it could.
- **Everything cut is written down.** A cut the user cannot see reads as an
  oversight. The plan names what was deferred and why, so cuts look like
  decisions.
- **The mockup shows this idea, never a wireframe.** Real copy, real sample
  data, real product name, color, and icons. Grey boxes labelled "content" are
  a failure of this Skill.
- **The one-pager is marketing, not documentation.** It sells the idea to a
  person who will never read the architecture. No component names, no stack
  names, no data flows.
- **`one-pager.pdf` is a genuine PDF.** Generated by a PDF tool, opens in a PDF
  reader, one page. A renamed `.md` or `.html` file is a failed run — see
  Generating the PDF.

## Procedure

1. Read `architecture.md` and `tech-stack.md`. Note the product name, the
   primary user, the core action, and the components that action touches.
2. **Name the riskiest assumption** — the one belief that, if wrong, makes the
   whole idea pointless. Everything downstream serves proving or breaking it.
3. Choose the Week 1 slice: the shortest path through the architecture that
   tests that assumption in front of a real user.
4. Write the checklist against `template.md` — see The MVP plan.
5. Build `mockup.html` — see The mockup.
6. Build `one-pager.pdf` — see The one-pager and Generating the PDF.
7. Save all three to `project-blueprint/`, creating the directory if needed. Do
   not overwrite existing files without saying so first.
8. Report as specified in Final report.

## The MVP plan

Follow `template.md` in this Skill's directory exactly — same sections, same
order, every time. It is what keeps two runs of this Skill comparable.

Writing the checklist:

- **Each item is one sitting's work**, phrased as a finished thing:
  "Paste-a-link form posts to `/api/score` and renders the returned number" —
  not "work on the frontend".
- **Each item names the real technology** from `tech-stack.md`. If the stack
  says Supabase, the item says Supabase.
- **Order by dependency, then by risk.** The step that could kill the idea goes
  as early as its dependencies allow — a fatal discovery on day 2 costs three
  days less than the same discovery on day 5.
- **Hardcode anything that is not the assumption under test.** Fake auth, one
  seeded user, a static list where a search will eventually go. Say explicitly
  in the item that it is faked, so it is never mistaken for done.
- **Day 5 ends with something demoable to another human**, not with a green
  test suite.

## The mockup

A single self-contained `mockup.html` file: inline `<style>`, no external
stylesheets, no CDN scripts, no remote images, no build step. Opening the file
in a browser must show a finished-looking screen.

Pick **one** screen — whichever a stranger would see first:

- If the idea sells to someone before they use it → a landing page: headline,
  subhead, what it does in three beats, one call to action.
- If the value is only visible in use → the core app view: the main workspace,
  populated with data.

Quality bar:

- **Real content for this idea.** Real product name, real headline, plausible
  sample rows with plausible names, numbers, dates, and statuses. Never lorem
  ipsum, never "Feature One / Feature Two".
- **A deliberate visual identity.** Choose a small palette (one primary, one
  accent, a neutral ramp) that suits this idea's audience, set type in a system
  font stack with real hierarchy, and use whitespace generously.
- **Icons inline as SVG**, or a restrained use of emoji where it fits the tone.
  No icon-font CDNs — they will not load.
- **Responsive and readable**: sensible max width, a layout that survives a
  narrow window, contrast that passes at a glance.
- **Static only.** No JavaScript needed for it to look right. A few lines for a
  hover or tab is fine; nothing that breaks if scripting is off.

Anti-template test: swap in a different idea — would this page need rewriting?
If not, it is a template and must be redone with this idea's specifics.

## The one-pager

One page. A person reads it in forty seconds and can repeat the idea to
someone else.

Content, in this order:

1. **Product name and a one-line what-it-is** — plain language, no jargon.
2. **What it does** — three or four short lines, each with an icon. Benefits in
   the user's words, not features in yours.
3. **Who needs it** — the specific person and the specific bad day they are
   having today without it.
4. **Why it matters** — exactly one sentence. The reason this is worth
   existing.
5. **A closing line or call to action** — what the reader should do next.

Rules: no component names, no technology names, no architecture. Short punchy
lines over paragraphs. Generous whitespace — a full page of dense text is a
failed one-pager. Use the mockup's palette so the two pieces look related.

## Generating the PDF

Write the styled one-page HTML to `project-blueprint/.one-pager/one-pager.html`
(A4 or Letter page size, print margins set in CSS), write **one** generator
script, then run **one** command to produce `project-blueprint/one-pager.pdf`.

Two commands are permitted; exactly one runs per session:

| Path | Script to write | Command to run |
|---|---|---|
| Python | `project-blueprint/.one-pager/build_pdf.py` | `python3 project-blueprint/.one-pager/build_pdf.py` |
| Node | `project-blueprint/.one-pager/build_pdf.js` | `node project-blueprint/.one-pager/build_pdf.js` |

Inside the script, use whatever is actually available on the machine — WeasyPrint
or ReportLab from Python, Puppeteer from Node, or a headless-Chrome
print-to-PDF invocation driven by the script. Prefer an HTML-rendering path
(WeasyPrint, Puppeteer, headless Chrome) so the PDF inherits the styling; fall
back to ReportLab and lay the page out directly if no HTML renderer is present.

If the first command fails because its library is missing, write the other
script and run the other command. Do not install packages, and do not reach for
any command outside the two above — if both fail, say so plainly, leave the
styled `one-pager.html` in place, and tell the user the one command they can
run to finish it.

Before reporting success, confirm the file exists, is non-empty, and is a real
PDF (it begins with `%PDF`). Never rename an `.md` or `.html` file to `.pdf`.

## Final report

After saving, report to the user:

1. **Every file created, with its exact path** — all three.
2. **One line on what each contains.**
3. **Which tool generated the PDF** — name the actual library or binary used
   (WeasyPrint, Puppeteer, headless Chrome, ReportLab), not just "the script".
4. **The riskiest assumption** the Week 1 slice is built to test, in one line.
