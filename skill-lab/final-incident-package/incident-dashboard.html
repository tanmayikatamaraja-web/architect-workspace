Why it broke

Three defects reached the extract

  • Blank region. A region-lookup dependency had a ~3-minute outage; the fallback wrote a blank instead of stopping — then the run died on that blank 9 minutes later.
  • Double-counted order. A database write timed out and was retried with no de-duplication key.
  • Stale everything. The failure stopped the pipeline's progress marker from advancing, so nothing has refreshed in ~4 days.

Common thread: every failure path degraded quietly instead of stopping. The quality gate caught these, not the pipeline.

What is not known

  • Owner — not assigned in the available evidence. Three related issues are unassigned or in backlog, the oldest open since 2026-06-11.
  • Resolution time — cannot be estimated from the available evidence.
  • Wider financial impact — not calculated. Figures here are arithmetic on the file, nothing more.
  • Duplicate blast radius — one row this time; the evidence does not establish whether a future retry duplicates one row or five.

Next business action

Confirm nothing downstream already consumed the 2026-08-03 extract, then keep the dashboard unpublished until a clean run passes the quality gate.

The pipeline defect is real, but it is not the first move — the extract is already on disk and already wrong, so the exposure question is who has seen it. Fixing the pipeline does not clean the artifact; the file must be regenerated by a healthy run and re-gated before publication.

Two decisions follow, both requiring an owner: assign the incident, and rule on refunds — the contract requires revenue > 0, but refunds are legitimate business events. Deleting them to satisfy the rule would overstate net revenue by $7,900.00, a worse error than the one being fixed.

Holding line if asked before then: last verified figures are from the 2026-08-02 load; the current extract failed validation and is withheld.
