# Executive Dashboard — Incident Brief

**Subject:** Orders/revenue dashboard, scheduled publish
**Decision:** **BLOCK — do not publish**
**Prepared:** 2026-08-06 · **Status:** open, unresolved

> Built from lab fixtures. The pipeline log and run metadata behind the
> root-cause section are synthetic exercise data, not captured production
> telemetry. The data-quality findings are computed from the actual file.

## Decision

**BLOCK.** The dashboard should not publish on schedule.

Two independent reasons, either sufficient on its own:

1. **The numbers are wrong.** The extract double-counts one order and carries
   an unresolved refund inside a measure defined as always-positive.
2. **The numbers are old.** No successful data load since 2026-08-02. Every
   row is at least 89 hours (3.7 days) old; the oldest is 165 hours.

These are measured from the file, not estimated. No wider financial impact has
been calculated, and none should be inferred from this brief.

## Why

The 2026-08-03 06:00 UTC pipeline run failed (exit 1) and has not succeeded
since. Three defects reached the extract:

| What went wrong | Effect on the dashboard |
|---|---|
| A region-lookup dependency had a ~3-minute outage; the pipeline's fallback wrote a blank region instead of stopping | One order, $1,490.00, belongs to no region |
| A database write timed out and was retried with no de-duplication key | One order counted twice, +$1,280.00 |
| The failure stopped the pipeline's progress marker from advancing | Nothing has refreshed for ~4 days |

The common thread: **each failure path degraded quietly instead of stopping.**
The pipeline logged all three as routine and continued. The data-quality gate,
not the pipeline, is what caught them.

## What is not known

Stated explicitly so nothing here is over-read:

- **Owner:** not assigned in the available evidence. The three related issues
  (`ETL-118`, `ETL-131`, `ETL-140`) are recorded as unassigned or backlog, two
  of them open since June and July.
- **Resolution time:** cannot be estimated from the available evidence.
- **Wider financial impact:** not calculated. The figures above are arithmetic
  on the file, nothing more.
- **Duplicate blast radius:** one row duplicated this time, but the evidence
  does not establish whether a future retry would duplicate one row or five.

## Next business action

**Confirm nothing downstream already consumed the 2026-08-03 extract**, then
keep the dashboard unpublished until a clean run passes the quality gate.

The pipeline defect is real but it is not the first move — the extract is
already on disk and already wrong, so the exposure question is who has seen it.
Fixing the pipeline does not clean the artifact; `orders.csv` must be
regenerated by a healthy run and re-gated before publication.

Two decisions follow, both requiring an owner:

1. **Assign the incident.** Three contributing issues are open and unassigned;
   the oldest has been open since 2026-06-11.
2. **Rule on refunds.** The contract requires revenue > 0, but refunds are
   legitimate. This is a definition question for the business, not a bug —
   deleting refunds to satisfy the rule would overstate net revenue by
   $7,900.00, a worse error than the one being fixed.

Recommended holding line if asked before then: *last verified figures are from
the 2026-08-02 load; the current extract failed validation and is withheld.*
